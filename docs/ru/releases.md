# Выпуски и CI для сопровождающего

[English](../releases.md) | **Русский**

Этот документ предназначен для сопровождающего и разработчиков. Обычным пользователям следует использовать [руководство по установке](installation.md); работать с GitHub Actions для установки ABX не требуется.

## Источник версии

У номера выпуска один источник:

```text
internal/app/VERSION
```

Приложение встраивает этот файл, а `scripts/package.sh` читает его при проверке тега и формировании имён артефактов.

## Локальная проверка выпуска

Перед публикацией версии:

```sh
make check
make live
```

`make live` следует запускать на репрезентативном поддерживаемом хосте, если менялось runtime/isolation поведение.

[Необязательные ручные проверки](manual-checks.md) доступны для диагностики или исследования конкретной проблемы. Их не требуется выполнять перед каждым релизом; они не добавляют условий выпуска.

Упаковка выполняется после появления тега (см. шаг 5 в разделе «Публикация версии»): релизному запуску скрипта требуется тег на `HEAD`. Те же архивы можно собрать и проверить без тега через `make package-check` — сборка идёт во временный каталог с теми же проверками; `make check` запускает её, поэтому дефект упаковки обнаруживается на ветке или в pull request, а не только на теге. Для проверки уже имеющихся архивов используйте `make package-smoke`.

`make package` читает `internal/app/VERSION` и передаёт работу `scripts/package.sh`. Packaging script не запускает тесты и не создаёт git tag. В git work tree он требует:

- совпадения переданного тега с `internal/app/VERSION`;
- чистого work tree без неотслеживаемых файлов, иначе бинарник из рабочего каталога может отличаться от source-архива, собранного из индекса;
- наличия именно этого тега на `HEAD`, иначе имя архива может описывать другое содержимое;
- попадания каждого tracked-пути верхнего уровня в source-архив.

Обычные сборки (`go build`, `make build-check`, `go test`) не ограничены: гейт касается только создания архивов. Вне git work tree скрипт предупреждает и упаковывает каталог как есть.

Скрипт создаёт:

| Файл | Содержимое |
|---|---|
| `abx-X.Y.Z-linux-amd64.tar.gz` | Статический Linux amd64 бинарник, всё дерево `docs/` на двух языках (и руководства пользователя, и документы для контрибьюторов), оба файла `README`, `CHANGELOG.md`, а также `LICENSE`/`THIRD_PARTY_LICENSES` |
| `abx-X.Y.Z-source.tar.gz` | Исходники, тесты, документация, Makefile, packaging script, workflows и корневые support-файлы (`go.mod`, `go.sum`, `.golangci.yml`, `.gitignore`, оба README, оба AGENTS-файла, `CHANGELOG.md`, лицензии) |
| `abx-X.Y.Z-SHA256SUMS` | SHA-256 бинарного и исходного архивов |

## GitHub Actions

CI относится к инфраструктуре разработки и выпуска, а не к пользовательской установке.

- `.github/workflows/check.yml` запускает `make check` для push и pull requests и переиспользуется release-workflow.
- `.github/workflows/live.yml` запускает настоящие Bubblewrap tests на CI runner.
- `.github/workflows/release.yml` запускается для тегов `v[0-9]*`, требует успеха check и live jobs, выполняет `scripts/package.sh` и загружает `dist/*` как workflow artifact.

Workflow artifact предназначен для проверки и дальнейшей публикации сопровождающим. Workflow **не создаёт** страницу релиза, и добавление публикации на странице выходит за рамки проекта — см. правило в `AGENTS.md`. Поэтому в шаге 7 сказано «канал релизов проекта» без указания сервиса: какой бы канал вы ни выбрали, результат один и тот же — три файла и их SHA-256, а пользователь должен суметь следовать [Установке](installation.md), не работая с Actions.

## Публикация версии

1. Перенесите нужные записи changelog из `Unreleased` в новую секцию `X.Y.Z`.
2. Измените `internal/app/VERSION` на то же значение `X.Y.Z`.
3. Выполните `make check` и нужные live tests.
4. Закоммитьте и отправьте release-изменения.
5. Когда CI ветки станет зелёным, создайте и отправьте annotated tag:

```sh
version=$(cat internal/app/VERSION)
tag="v$version"
git tag -a "$tag" -m "ABX $version"
git push origin "$tag"
```

Ожидание CI ветки — рекомендация, а не проверяемое условие: ни в репозитории,
ни в конвейерах нет сверки, что помеченный коммит вообще был зелёным на ветке.
Гарантия приходит на следующем шаге: workflow тега заново прогоняет и check, и
live на самом помеченном коммите и не собирает ничего, пока оба не пройдут.
Поэтому отправленный слишком рано тег — не риск публикации, а лишний прогон.

6. Убедитесь, что tag workflow прошёл. Он собирает архивы и затем выполняет `make package-smoke`: сверяет манифест сумм, распаковывает оба архива и проверяет обязательные списки файлов. Скачайте его workflow artifact: имена файлов архивов внутри сохраняются как `abx-X.Y.Z-*`, поэтому `(cd <скачанное> && sha256sum -c "abx-X.Y.Z-SHA256SUMS")` проверяет их без переименования. Затем сделайте smoke-test бинарника.
7. Опубликуйте проверенные бинарный архив, source archive и checksum manifest через release-канал проекта — см. примечание выше о том, что это значит. Сообщите значения SHA-256.

Локальную упаковку можно репетировать без тега через `make package-check`; `make package-smoke` проверяет уже готовые архивы в `dist/`, а сама `make package` требует тега, поэтому запускайте её после шага 5.

Не переносите уже опубликованный version tag на другое содержимое. Последующие исправления выпускайте новой версией.

Отправка всех тегов разом через `git push --force` не запускает workflow: теги на remote сдвигаются, а GitHub не запускает ничего — ни проверки, ни живых тестов, ни артефактов релиза, ни ошибки. Выглядит как сломанный Actions. Одиночный перенацеленный тег через `--force` не проверен. Отправляйте теги без `--force`; ветку при замене истории двигать принудительно можно.

Метаданные архивов не нормализованы для побайтовой воспроизводимости, build attestation текущий workflow не создаёт.
