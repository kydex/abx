# Модель защиты

[English](../security.md) | **Русский**

Этот документ описывает границы, которые обеспечивает текущая реализация. Обычные команды и примеры находятся в [Использовании](usage.md).

## Что изолирует ABX

`run`, `shell` и `work` используют одну политику песочницы. В `shell` просто отсутствует mount проекта и запускается login shell учётной записи. `work` подключает тот же проект, что `run`, но запускает login shell в `/workspace`.

| Ресурс | `run` / `work` / `verify` | `shell` |
|---|---|---|
| Home профиля | `/home/agent`, запись | То же |
| Текущий проект | `/workspace`, запись, cwd | Не подключается |
| Shared skills, если настроены | `/home/agent/.agents/skills`, только чтение | То же |
| Выбранные системные файлы | Только чтение | То же |
| `/tmp`, `/var/tmp`, `/run` | Приватные tmpfs, 4 GiB на каждый | То же |
| `/proc`, `/dev` | Приватные/отдельные представления | То же |
| Сеть | Общая с хостом | Общая с хостом |

Bubblewrap создаёт отдельные user, mount, PID, IPC и UTS namespaces и задаёт hostname `abx`. ABX также передаёт `--disable-userns`, поэтому код внутри песочницы не может создать ещё один user namespace через поддерживаемый Bubblewrap механизм. ABX передаёт `--die-with-parent`: процессы песочницы получают SIGKILL при завершении лаунчера. Это касается работающей песочницы; сигнал, пришедший во время настройки песочницы Bubblewrap, до вооружения parent-death signal, может оставить песочницу-сироту. Стоит назвать прямо ещё два ограничения. Обработчик сигнала Bubblewrap устанавливается только для `SIGCHLD`, поэтому любой пересланный ABX сигнал завершает монитор действием по умолчанию, что вооружает parent-death signal и убивает payload SIGKILL даже во время работы обработчика завершения — терминальный `Ctrl+C` в `shell` или `work` ведёт себя так же, потому что ABX не передаёт ни `--new-session`, ни отдельную процессную группу, и сигнал достигает монитора и payload одновременно. Фоновая задача, запущенная внутри песочницы, может пережить сессию и удерживать свои tmpfs и доступ к сети. Проверено на живом хосте: `--die-with-parent` убивает команду, которую запустил Bubblewrap, тогда как процесс, отправленный в фон заранее, продолжает работать после её гибели. Родительский сигнал не наследуется через `fork(2)`, поэтому останавливает фоновый процесс не он.

Окружение начинается с пустого. ABX сам задаёт HOME, USER/LOGNAME, SHELL, PWD, TMPDIR, XDG-пути, PATH и расположения npm/Bun. С хоста передаются только настройки терминала, локали и цвета: `TERM`, `COLORTERM`, `LANG`, `LANGUAGE`, `TZ`, `NO_COLOR`, `FORCE_COLOR` и корректные `LC_*`.

Произвольные переменные окружения хоста, включая proxy-, credential- и loader/runtime-переменные, автоматически не наследуются. Сокет SSH agent также не подключается.

## Какие файлы хоста видны

ABX подключает `/usr` только для чтения и, если они существуют, совместимые пути `/bin`, `/sbin`, `/lib` и `/lib64`. Также подключается ограниченный набор ресурсов `/etc` (при наличии на хосте), необходимый обычным консольным программам: данные пользователей и групп, DNS-настройки, сертификаты, timezone, конфигурация dynamic loader, данные ОС, shells и alternatives. Отсутствующие файлы пропускаются молча; `abx inspect` печатает фактически обнаруженный список.

Весь host `/etc`, home пользователя хоста и host `/run` в песочницу не подключаются.

ABX не подключает home учётной записи целиком. С записью подключается выбранный профиль; `run` и `work` дополнительно подключают с записью только выбранный текущий проект.

## Проверки файловой системы

ABX считает своё хранилище и профили приватными данными. Обязательные каталоги ABX должны быть реальными каталогами, принадлежать запускающему пользователю и иметь точный режим `0700` там, где этого требует политика. Небезопасные существующие объекты отклоняются и не исправляются автоматически.

Текущий проект канонизируется до использования. ABX отклоняет проекты, которые пересекаются с корнем файловой системы, самим home пользователя, хранилищем ABX, защищёнными системными деревьями или чувствительными домашними каталогами (`.config`, `.ssh`, `.gnupg`, `dotfiles`, `.aws`, `.docker`, `.kube`, `.pki`, `.cache`, `.netrc`, `.git-credentials`, `.password-store`, `.npmrc`, `.gem/credentials`, `.local/share/keyrings`, `.mozilla` и `.thunderbird`).

Выбранные host sources открываются и удерживаются по file descriptor. Перед выполнением ABX повторно их проверяет, а Bubblewrap получает bind sources через удерживаемые FD вместо повторного открытия того же пути. Это уменьшает важные окна pathname-replacement race между проверкой и mount, но не делает содержимое writable файлов и каталогов неизменяемым. Перед выполнением ABX также выставляет флаг close-on-exec всем унаследованным дескрипторам, кроме стандартных потоков и тех, что передаются дочернему процессу: удерживаемых источников монтирования, удерживаемого бинарника Bubblewrap и, для `verify`, дескриптора `/proc/self/exe`. Остальные дескрипторы помечаются, включая собственные удерживаемые дескрипторы хранилища ABX, которые источниками монтирования никогда не бывают, поэтому посторонние дескрипторы хоста не попадают в песочницу; исходные флаги затем восстанавливаются на стороне лаунчера.

Внутренний sandbox `Plan` структурно проверяется при построении и ещё раз перед переводом в аргументы Bubblewrap. Валидатор проверяет ожидаемые системные источники, private mounts, роли профиля и проекта, optional skills mount, рабочий каталог, команду и layout проверочного probe.

ABX дополнительно проверяет объекты хоста, от которых зависит: два исполняемых, базу учётных данных, которую читает, домашний каталог учётной записи, собственное хранилище и место, где действительно живёт исполняемый агента.

| Объект | Проверка |
|---|---|
| `/usr/bin/bwrap` | Обычный файл, исполняемый, без setuid/setgid/sticky-битов, недоступен для записи group/other, принадлежит root; перед запуском должен указывать на тот же inode |
| Login shell из `/etc/passwd` | Разрешённая цель — обычный файл, исполняемый запускающим пользователем, недоступный для записи group/other, без setuid/setgid/sticky-битов; и путь из passwd, и его разрешённая цель должны быть видны в песочнице |
| Домашний каталог из `/etc/passwd` | Настоящий каталог, недоступный для записи посторонним, принадлежит запускающему UID |
| Каталоги хранилища и профилей ABX | Настоящие каталоги, точный режим `0700` без setuid/setgid/sticky-битов, принадлежат запускающему UID |
| Исполняемый файл профиля | Его настоящий файл должен быть достижим из того, что ABX подключает, чтобы он существовал внутри песочницы, а не падал бы при запуске с виной на инструмент |

База учётных записей читается двумя разными путями, и какие файлы они читают, зависит от того,
как собрана ABX. Оболочка всегда читается из литерального `/etc/passwd`. Сама запись учётной записи
(`home`, `username`) приходит из `os/user.LookupId`. Поставляемый статический бинарник собирается
с `CGO_ENABLED=0`, и там `os/user` использует собственную реализацию, читающую тот же литеральный
`/etc/passwd`, — строка таблицы покрывает оба пути. При сборке с cgo `LookupId` идёт через NSS и
читает `nsswitch.conf`; там хост, разрешающий `passwd` через `sss` или `ldap`, ломает поиск оболочки,
хотя `id` и `getent` по-прежнему показывают учётную запись верно, и ABX отказывает. Собирайте из
исходников с `CGO_ENABLED=0`, чтобы оба пути оставались под проверками. Локальная запись в
`/etc/passwd` для UID запускающего пользователя требуется в любом случае; это требование
продублировано в [Установке](installation.md).

Владелец login shell сознательно не требуется: пользовательские оболочки тоже живут в системных путях (например `/usr/local/bin`), а правило видимости и так ограничивает их смонтированными системными деревьями.

Смонтированный `/etc/shells` предназначен для программ внутри песочницы; проверка login shell его не использует. Встроенные проверки выше строже на большинстве систем, а `/etc/shells` в некоторых дистрибутивах содержит несистемные пути.

База учётных записей запрашивается два раза по имени: один раз для проверки режима и ещё раз для чтения содержимого. Каждый запрос заново разрешает путь, поэтому, в отличие от бинарника Bubblewrap, который ABX открывает один раз и держит дескриптор до запуска, ничто не закрепляет проверенный файл и прочитанный файл за одним inode. Подмена файла между двумя запросами требует права записи в `/etc/passwd`, а проверка режима сама запрещает её для group и other, то есть нужен владелец. Хост, чью базу учётных записей принадлежит или может переписать непривилегированный пользователь, поэтому вне того, что ABX защищает: этот пользователь уже контролирует ту учётную запись, которую читает ABX, и тот же файл читается ещё раз через `os/user` вообще без этих проверок. Один дескриптор на обе проверки закрыл бы окно и ничего больше бы не изменил.

## Shared skills

Если `<хранилище ABX>/shared/agents/skills` существует и проходит проверки, он подключается только для чтения как `/home/agent/.agents/skills`.

Shared path необязателен. ABX проверяет нужные каталоги и отклоняет небезопасное перенаправление через symlink в mount target профиля. Подготовка может оставить пустые `.agents` / `.agents/skills` в writable профиле; само shared-содержимое остаётся read-only mount.

## Проверка через verify

`abx verify <profile>` запускает тот же sandbox backend, что обычные сессии, с одним дополнительным фиксированным read-only probe executable. Команда проверяет наблюдаемые namespaces, cwd, hostname, окружение, private mounts/views, read-only ресурсы, возможность записи в профиль и проект и выбранные границы доступа.

Точка входа `__probe` приватна: она работает только внутри песочницы, где `/abx-probe` — read-only mount бинарника ABX, а вызовы на хосте отклоняются.

Для ресурсов только для чтения probe проверяет флаги каждой выбранной точки монтирования в `/proc/self/mountinfo`. Он не проверяет каждый вложенный mount отдельно и не пробует запись в эти ресурсы. Ограничение записи обеспечивает Bubblewrap; `PASS` для родительской точки монтирования не является отдельной проверкой всех вложенных mounts.

Успешный `verify` подтверждает состояние конкретного запуска и хоста в этот момент. Это не постоянная гарантия для всех будущих запусков.

## Оставшиеся риски

- Агент может изменять и удалять всё в writable профиле и выбранном проекте.
- Сеть общая, поэтому sandbox-код может обращаться к сетевым сервисам, доступным хосту, и передавать наружу данные, которые способен прочитать.
- Содержимое проекта рекурсивно не очищается. В проекте могут быть sockets, hard links, nested mounts или намеренно опасные исходники/build scripts.
- Песочница использует терминал вызывающего пользователя напрямую. Terminal escape sequences и зависящие от хоста terminal ioctls остаются частью поверхности риска; отдельной изоляции terminal session ABX не предоставляет.
- ABX не задаёт seccomp policy и resource quotas. Защита по-прежнему зависит от ядра Linux, Bubblewrap, конфигурации хоста и программ внутри песочницы.
- Враждебный процесс, одновременно работающий на хосте под тем же UID, всё ещё может пытаться менять доступные пользователю данные. Retained descriptors и revalidation уменьшают важные pathname-race, но не являются полной моделью защиты от same-UID adversary. Известные остаточные окна — замена agent-исполняемого файла между проверкой и выполнением, изменение записей профилей между листингом и инспекцией, появление компонентов data-base между каноникализацией и использованием, а также перепроверки метаданных по pathname — приняты как задокументированные и не учитываются как findings. Mount всегда используют удерживаемые дескрипторы, поэтому поздняя подмена не может перенаправить то, что смонтировано.
- Некоторые ошибки могут оставить созданные каталоги или verification probe files. ABX не делает рекурсивный автоматический rollback, который мог бы удалить посторонние пользовательские данные.

## Принятые компромиссы

Следующие ограничения являются намеренными границами текущей реализации, а не незавершёнными задачами:

- **Изоляция во время выполнения:** окружение очищается только от NUL-байтов, поэтому значение с переводом строки доходит до агента без изменений; `TZ`, `LANG`, `LANGUAGE` и `LC_*` пересылаются без ограничений, а libc читает их как файлы в `/usr/share`. Личность процесса внутри песочницы не описана и не проверяется. Сеть общая, терминал вызывающего пользователя используется напрямую без terminal-session isolation, seccomp policy и cgroup resource quotas не задаются (потолок 4 GiB ABX задаёт только своим трём tmpfs-монтам `/tmp`, `/var/tmp` и `/run`; всё остальное, что песочница получает записываемым без ограничения, — mount `--dev` со своим tmpfs и корень песочницы, который создаёт Bubblewrap, для которого ABX размера не задаёт вовсе), содержимое проектов и вложенные mounts не очищаются рекурсивно.
- **Допущения о путях:** проекты, пересекающиеся с защищёнными системными деревьями, отклоняются вместе с подкаталогами (`/bin`, `/boot`, `/dev`, `/etc`, `/lib`, `/lib64`, `/opt`, `/proc`, `/root`, `/run`, `/sbin`, `/sys`, `/usr`, `/var`, `/srv`, `/mnt`, `/media`, `/snap`); `/tmp` отклоняется только как точный путь, а `/var/tmp` и `/dev/shm` — как подкаталоги защищённых деревьев; чужие домашние каталоги вне реального home отклоняются только под `/home`; гонка с промежуточным symlink проекта и startup-race при раннем сигнале закрыты не полностью; symlink-и системных ресурсов считаются доверенной конфигурацией хоста; denylist чувствительных домашних путей намеренно конечен. Домашний каталог проверяется на владельца и недоступность для записи посторонним, но не на setuid или setgid, в отличие от соседнего предка хранилища, и промежуточный каталог shared skills не проверяется на точный режим. Недостающие компоненты хранилища создаются с режимом `0700`; ближайший существующий предок кастомного `XDG_DATA_HOME` уже должен быть каталогом, принадлежащим пользователю и не доступным для записи посторонним, если не несёт sticky-бит, и не должен нести setuid или setgid: setgid-каталог делает всё созданное внутри хранилища наследовать группу, которую проверка не смотрит. Домашний каталог должен принадлежать запускающему UID. `/etc/passwd` не обязан принадлежать root: это должен быть обычный файл без setuid/setgid/sticky-битов, недоступный для записи group и other, потому что запись из него называет домашний каталог, в котором работает сессия. Подмена файла между двумя запросами требует владельца, так как проверка режима запрещает запись для group и other, — см. абзац про двойной запрос выше. Group-writable предки принимаются: это командная политика, а не атака, и отказ ломает машины с umask 002. Это принятие распространяется и на промежуточные каталоги login shell, исполняемого файла агента и монтируемых системных источников: ABX проверяет конечный файл, а не ведущие к нему каталоги, поэтому участник группы с правом записи в родительский каталог мог бы подменить бинарь, который запускает сессия. Закрытие этого окна сломало бы те же командные машины, поэтому риск принят как задокументированный. Исполняемый файл профиля может быть симлинком в подключённый системный путь вроде `/usr` или внутрь самого профиля — так его ставит пакетный менеджер; ссылка, ведущая и туда, и сюда, отвергается при разборе профиля, потому что там ничего не подключено и сессия упала бы уже при запуске. Текущий проект вообще не ограничен ни владельцем, ни режимом — командные checkout'ы, общие тома и файловые системы без POSIX-режимов (где всё `0777`) легитимны.
- **Проверка и диагностика:** `verify` является smoke-test, а не полной security attestation; metadata probe передаётся через argv; cleanup races и residue остаются best-effort; ошибки setup Bubblewrap и payload exit code `1` не различаются; retained FD Bubblewrap оставлен.
- **Release и CI:** упаковка предполагает clean checkout, versions actions и tools плавающие, live tests являются gate для release tags, но не для pull requests, а archives не воспроизводимы побайтово и не подписаны/attested.

Важные данные проекта и профиля резервируйте обычным для себя способом: writable-доступ к ним является намеренным.
