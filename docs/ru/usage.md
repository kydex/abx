# Использование

[English](../usage.md) | **Русский**

Команды `abx` запускайте во внешнем терминале от обычного пользователя. `abx shell` используйте, когда нужно установить или настроить программы внутри профиля.

## Какую команду выбрать

| Задача | Команда |
|---|---|
| Установить или настроить инструменты без доступа к проекту | `abx shell <profile>` |
| Сразу запустить executable профиля в текущем проекте | `abx run <profile>` |
| Открыть shell с доступом к текущему проекту | `abx work <profile>` |

Любая команда, принимающая профиль, принимает ровно одно имя; больше принимает только `run`, и только после `--`. `shell`, `work`, `inspect`, `verify` и подкоманды `profile` отвергают любой лишний аргумент. `--` — это аргумент, а не разделитель, который можно оставить висеть: его принимает только `run` и только чтобы ввести аргументы для агента (`abx run <profile> -- <argument> [additional arguments]`). `abx shell <profile> --` — ошибка. Голый `--` без ничего после него принимается и ведёт себя ровно как отсутствие разделителя.

`abx` без аргументов печатает ту же справку, что и `abx help`. `-h`/`--help` и `-v`/`--version` — команды только на первой позиции: `abx --help` и `abx -v` работают, а `abx profile create demo --version` считается ошибкой аргументов, а не запросом версии.

## Профили

Профиль — это постоянный домашний каталог агента или набора связанных инструментов. `abx run <profile>` по-прежнему запускает исполняемый файл с тем же именем, что и профиль; этот основной исполняемый файл может запускать другие agent CLI, установленные в том же профиле.

```sh
abx profile create opencode
abx profile show opencode
abx profile list
```

Имя профиля содержит от 1 до 64 ASCII-символов. Первый символ должен быть буквой или цифрой; далее также разрешены `.`, `_` и `-`.

По умолчанию профили хранятся в:

```text
~/.local/share/abx/profiles/<name>
```

ABX использует домашний каталог из `/etc/passwd`, а не переменную `HOME` внешнего окружения. Если `XDG_DATA_HOME` — абсолютный путь, корнем хранения становится `<XDG_DATA_HOME>/abx`. Относительные значения игнорируются.

`profile create` создаёт новый пустой профиль и не перезаписывает существующий. `profile show` показывает фактический путь и состояние одноимённого основного исполняемого файла и необязательных shared skills. `profile list` выводит список профилей. Записи с недопустимыми именами пропускаются молча. Профиль с небезопасной раскладкой останавливает перечисление, а не показывается как пригодный: команда печатает ошибку и больше ничего, а `profile show <profile>` называет причину для этого профиля. Перечисление останавливается намеренно — показать профиль, которым нельзя пользоваться, хуже, чем показать меньше.

`profile show` показывает отсутствующий профиль как `State: absent` и возвращает код `0`; по коду завершения нельзя проверять существование профиля. `profile list` ничего не печатает и возвращает код `0`, когда профилей нет; вывод так же пуст, когда все записи пропущены как недопустимые. Доступность команды определяется проверкой файла на хосте и не подтверждает запуск инструмента или песочницы. Отчёт охватывает точку входа и shared skills; login shell берётся из `/etc/passwd` хоста и разрешается только при запуске сессии, а не командой `profile show`. Ошибки обязательных проверок структуры хранилища приводят к неуспеху команды.

Негодные shared skills ведут себя иначе: `profile show` и `profile list` не падают и показывают их как негодные, а причину называет `profile show`, тогда как все три режима сессий монтируют shared skills, когда те настроены, и отказываются стартовать, пока каталог не исправлен (см. Shared skills).

ABX не переименовывает, не переносит и не удаляет профили автоматически.

## Установка агентов и инструментов в профиль

Откройте оболочку профиля:

```sh
abx shell opencode
```

Внутри песочницы:

- `HOME=/home/agent`;
- рабочий каталог — `/home/agent`;
- проект хоста не подключён;
- `/home/agent/.local/bin` и каталог шимов mise стоят в начале PATH, за ними — `/home/agent/.bun/bin` и `/home/agent/bin`;
- системные каталоги доступны только для чтения.

Используйте системно установленный менеджер пакетов, видимый внутри песочницы. Например, OpenCode через Bun:

```sh
bun add -g opencode-ai
opencode --version
```

Или через npm:

```sh
npm install -g opencode-ai --allow-scripts=opencode-ai
opencode --version
```

После установки выйдите из оболочки профиля:

```sh
exit
```

Программы, установленные только в home пользователя на хосте, автоматически внутри песочницы не появляются. Устанавливайте инструменты агента в профиль или используйте системно установленные программы из каталогов, доступных только для чтения.

### Профиль с несколькими агентами: Herdr

В одном профиле можно держать Herdr и несколько agent CLI. Для detach/reattach используйте `work`, чтобы после выхода из клиента оставаться в shell той же песочницы.

На хосте создайте профиль и откройте shell для установки:

```sh
abx profile create herdr
abx shell herdr
```

Внутри ABX установите инструменты, затем вернитесь на хост:

```sh
curl -fsSL https://herdr.dev/install.sh | sh
bun add -g opencode-ai
# Pi и другие agent CLI установите их обычным способом.
exit
```

На хосте перейдите в проект и откройте рабочий shell:

```sh
cd "$HOME/code/my-project"
abx work herdr
```

Внутри ABX запустите Herdr:

```sh
herdr
```

`work` оставляет внешний shell внутри песочницы после detach Herdr. Herdr может запускать OpenCode, Pi и другие CLI из того же профиля: у них общий PATH и доступ к проекту в `/workspace`. Для прямого запуска без внешнего shell используйте на хосте `abx run herdr`.

Herdr может открыть первый workspace в `/home/agent`, хотя `/workspace` уже подключён. В таком случае создайте и сразу откройте workspace проекта явно из самого Herdr:

```sh
herdr workspace create --cwd /workspace --label project --focus
```

После этого workspace Herdr будет работать с проектом, который ABX подключил в `/workspace`.

Herdr и запущенные им агенты используют общий `/home/agent` и один доступный с записью проект, поэтому весь профиль следует считать единой границей доверия. Если нужно разделить состояние или учётные данные, используйте отдельные профили.

Detach/reattach Herdr работает обычно, пока жива сама песочница ABX. Если завершить сессию ABX, процессы песочницы также завершаются; при следующем запуске Herdr может восстановить сохранённое состояние сессии, но это не следует считать продолжением тех же живых процессов агентов.

## Запуск агента в проекте

Имя профиля в `run` должно совпадать с именем исполняемого файла. ABX ищет его в таком порядке:

```text
/home/agent/.local/bin/<name>
/home/agent/.local/share/mise/shims/<name>
/home/agent/.bun/bin/<name>
/home/agent/bin/<name>
```

Инструменты, установленные через mise, находятся через каталог его шимов, без ручного создания ссылок. Сам бинарник `mise` тоже должен быть доступен внутри песочницы: установка по умолчанию в `~/.local/bin` и системные пути под `/usr` работают, а кастомные места вне монтируемых путей громко падают при запуске шима.

Во внешнем терминале перейдите в проект:

```sh
cd "$HOME/code/my-project"
abx run opencode
```

Текущий каталог хоста становится доступным с записью как `/workspace`, и агент запускается с `/workspace` как рабочим каталогом.

ABX отклоняет проекты, которые могли бы открыть чувствительные или системные пути: корень файловой системы, сам home пользователя, хранилище ABX, защищённые системные деревья и отдельные чувствительные каталоги вроде `.ssh`, `.gnupg` и `.config`. Используйте отдельный каталог проекта, например `~/code/project`.

### Символические ссылки на исполняемый файл

`run` и `inspect` проверяют основной исполняемый файл профиля по путям хоста до запуска песочницы. Состояние команды в `profile show` и `profile list` определяется той же проверкой. ABX не переводит цели символических ссылок между путями хоста и песочницы.

Абсолютная ссылка вроде `.local/bin/demo -> /home/agent/.local/lib/demo` может работать внутри песочницы, но считаться недоступной на хосте. И наоборот: ссылка на абсолютный путь профиля на хосте может пройти проверку, но не работать внутри песочницы, где этот путь обычно скрыт. Кандидат, не прошедший эти проверки файла, пропускается в пользу следующего пригодного файла в порядке поиска. На кандидате, прошедшем их, поиск заканчивается: если его цель разрешается вне профиля и смонтированных системных источников, команда отклоняется с этой ошибкой, а не переходит к следующему кандидату.

Для ссылок между файлами внутри профиля используйте относительные цели, которые остаются внутри профиля, например `.local/bin/demo -> ../lib/demo`. Вся цепочка ссылок должна оставаться корректной. Избегайте ссылок на абсолютный путь профиля на хосте.

Если установленный инструмент работает внутри песочницы, но не проходит проверку на хосте, откройте `abx work <profile>` и запустите его там; когда доступ к проекту не нужен, используйте `abx shell <profile>`. Обе команды не требуют одноимённого исполняемого файла профиля. Обе команды принимают только имя профиля, без аргументов после `--`.

Для прямого `run` можно также использовать обычный исполняемый скрипт-обёртку с именем профиля в одном из каталогов поиска. Он может вызывать сам инструмент по пути внутри песочницы и передавать ему аргументы, например:

```sh
#!/bin/sh
exec /home/agent/tools/demo/bin/demo "$@"
```

Замените путь из примера фактическим путём инструмента внутри песочницы. Обёртка должна иметь право исполнения и вызывать сам инструмент, а не себя повторно.

### Аргументы агента

Всё после `--` передаётся агенту напрямую:

```sh
abx run opencode -- --version
abx run opencode -- "argument with spaces"
```

ABX не передаёт эти аргументы через дополнительную shell-команду. Ядро ограничивает один аргумент 32 страницами — обычно 128 КиБ на хосте со страницей 4 КиБ. Значение длиннее падает при exec с `argument list too long`; ABX не проверяет аргументы `run` заранее.

## Shell в проекте: work

На хосте:

```sh
cd "$HOME/code/my-project"
abx work herdr
```

Внутри ABX:

```sh
herdr
```

`work` открывает login shell с профилем в `/home/agent` и текущим каталогом хоста, доступным с записью в `/workspace`. Начальные cwd и `PWD` — `/workspace`; применяются те же проверки пути проекта и ограничения изоляции, что у `run`. Корень Git-репозитория автоматически не ищется.

Профиль должен существовать, но установленная программа с именем профиля не требуется. Внутри можно запускать любые доступные инструменты. `work` принимает только имя профиля, без аргументов после `--`. Для установки и обслуживания без доступа к проекту используйте прежний `abx shell <profile>`.

Как и `shell`, команда запускает shell из passwd с аргументом `-l`; интерактивность не форсируется через `-i`. При запуске из терминала это обычная интерактивная сессия. Startup-файлы профиля могут изменить начальный рабочий каталог.

Для Herdr запускайте `herdr` обычной командой, без `exec`: после detach управление возвращается во внешний shell внутри ABX. Повторный `herdr` в этой же живой `work`-сессии позволяет подключиться к работающему серверу. Не используйте `exec herdr`, если после detach хотите вернуться во внешний shell ABX: `exec` заменяет этот shell. Завершение сессии ABX завершает процессы песочницы; новый `abx work` не продолжает те же живые процессы. Файлы профиля и проекта сохраняются, приватные временные каталоги создаются заново.

## Просмотр плана запуска

```sh
abx inspect opencode
```

`inspect` выбирает тот же профиль, агент, проект, системные источники и окружение, что обычный `run`, а затем печатает план без запуска Bubblewrap. Он требует executable профиля и не показывает план `shell` или `work`. Как и `work`, принимает только имя профиля, без аргументов после `--`.

Вывод содержит:

- рабочий каталог и команду;
- подробные операции монтирования;
- переменные окружения;
- сводку изоляции;
- пути с записью и приватные пути песочницы, размеры приватных tmpfs и базовые каталоги, оставленные записываемым scratch.

`inspect` помогает понять, что ABX собирается запустить. Это не проверка реально работающей песочницы. Режим прав и размер tmpfs выводятся только при явном назначении; отсутствие режима не означает права `0000`.

## Проверка песочницы

Из каталога проекта:

```sh
abx verify opencode
```

Для `verify` **не требуется** установленный исполняемый файл агента. Команда запускает настоящую песочницу Bubblewrap и проверяет основные свойства обычной сессии: namespaces, mounts профиля и проекта с записью, приватные временные каталоги и устройства, системные ресурсы только для чтения, окружение, cwd и границы доступа.

Успешная проверка заканчивается строкой:

```text
Verification passed; temporary probe files removed.
```

Проверка выполняется с дедлайном 30 секунд на открытие инструмента и работу песочницы; хостовое наблюдение и зачистку он не прерывает. Первая сборка плана проверяет форму до старта дедлайна. При таймауте ABX сообщает `execution cancelled` и возвращает код `1`. Строки проверок печатаются сразу, как только собраны все наблюдения, а не по ходу работы пробы: прерванная во время наблюдений проба не напечатает ничего. Как и `work`, `verify` принимает только имя профиля, без аргументов после `--`.

Отдельные проверки используют `PASS`, `FAIL`, `UNAVAILABLE` и `N/A`. `N/A` ожидаем, когда shared skills не настроены. Ошибка или невозможность выполнить обязательную проверку приводит к неуспеху `verify`. В деталях расхождений указываются ожидаемое и наблюдаемое состояния, когда они доступны. При расхождении окружения выводятся только имена отличающихся переменных, без их значений.

Вход, который лаунчер передаёт пробнику, ограничен 64 KiB, включая окружение; более длинный вход ABX отклоняет до старта песочницы, называя его размер, вместо молчаливого усечения или сырой ошибки `execve`.

Проверки read-only смотрят флаги выбранных точек монтирования; каждый вложенный mount отдельно не проверяется. Ограничение записи обеспечивает Bubblewrap. Подробнее — [границы проверки](security.md#проверка-через-verify).

Во время проверки ABX временно создаёт проверочные файлы в настоящем home, домашнем каталоге выбранного профиля и выбранном проекте и удаляет их до финального сообщения об успехе. Принудительное завершение процесса или сбой хоста могут оставить временные файлы.

Точка входа `__probe` приватна: она работает только внутри песочницы как `/abx-probe`, а вызовы на хосте отклоняются.

## Shared skills

Shared skills необязательны. ABX ищет их в:

```text
<хранилище ABX>/shared/agents/skills
```

Если каталог настроен, он подключается только для чтения в каждый профиль как:

```text
/home/agent/.agents/skills
```

Для стандартного хранилища:

```sh
# ABX использует home из passwd, а не $HOME оболочки.
abx_root="$(awk -F: -v uid="$(id -u)" '$3 == uid { print $6; exit }' /etc/passwd)/.local/share/abx"
mkdir -p "$abx_root/shared/agents/skills"
chmod 700 "$abx_root" "$abx_root/shared"
```

Компоненты пути `shared`, `agents` и `skills` должны быть реальными каталогами там, где ABX это требует; небезопасное перенаправление через symlink отклоняется. Каталог `shared` должен принадлежать запускающему пользователю и иметь точный режим `0700`. Корень хранилища (`$abx_root`) также должен принадлежать запускающему пользователю и иметь точный режим `0700`; `mkdir -p` создаёт недостающих предков с режимом по умолчанию, поэтому выставьте его явно — иначе `profile`, `run`, `shell`, `work`, `inspect` и `verify` завершатся ошибкой `private directory "<путь>" must have exact mode 0700`. В кавычках полный путь — во всех командах, кроме `profile create`. Эта команда обходит компоненты хранилища по порядку, останавливается на первом негодном и называет полный путь в контексте подготовки, а компонент — в причине. `help` и `version` продолжают работать.

При использовании skills ABX может создать внутри профиля `.agents` и пустую точку монтирования `.agents/skills`. Это служебные каталоги для подготовки монтирования, а не копии shared skills.

## Другое хранилище

Чтобы держать профили в другом месте, задавайте один и тот же абсолютный `XDG_DATA_HOME` для всех связанных команд:

```sh
ABX_DATA="$HOME/abx-data"
env XDG_DATA_HOME="$ABX_DATA" abx profile create opencode
env XDG_DATA_HOME="$ABX_DATA" abx shell opencode
env XDG_DATA_HOME="$ABX_DATA" abx run opencode
```

ABX сам добавляет компонент `abx`, поэтому в этом примере профили находятся в `$ABX_DATA/abx/profiles`.

База — и по умолчанию, и выбранная через `XDG_DATA_HOME`, — должна удовлетворять шести условиям, у каждого своё сообщение об отказе: она не должна быть корнем файловой системы (`data base "<путь>" is the filesystem root`); не должна находиться внутри чувствительного домашнего каталога вроде `~/.config` или `~/.ssh` (`data base "<путь>" overlaps sensitive home tree "<путь>"`); а её ближайший существующий предок должен быть каталогом (`data base ancestor "<путь>" is not a directory`), принадлежать вам (`data base ancestor "<путь>" is not owned by the invoking user`), не быть доступным для записи посторонним, если не несёт sticky-бит (`data base ancestor "<путь>" is world-writable`), и не иметь битов setuid или setgid (`data base ancestor "<путь>" has a setuid or setgid bit`). Недостающие компоненты ниже предка создаются автоматически с режимом `0700`, поэтому существовать должен только предок.

Изменение `XDG_DATA_HOME` выбирает другое хранилище и не переносит существующие профили.

## Окружение внутри песочницы

ABX начинает с чистого окружения. Значения `HOME`, `USER`, `LOGNAME`, `SHELL`, `PWD`, PATH, XDG-каталогов, `TMPDIR`, `NPM_CONFIG_PREFIX` и `BUN_INSTALL` профиля задаются самим ABX.

С хоста при наличии передаются только:

```text
TERM COLORTERM LANG LANGUAGE TZ NO_COLOR FORCE_COLOR LC_*
```

`LC_*` — это любое имя такого вида, `LC_` и следом один или несколько символов из `A-Z`, `0-9` или `_`, а не только локальные настройки; значение с NUL-байтом не передаётся, а содержимое в остальном не проверяется.

Передаваемое значение ограничено 64 KiB: более длинное останавливает сессию с ошибкой, называющей переменную.

Произвольные переменные окружения хоста, включая proxy- и credential-переменные, автоматически не копируются; сокет SSH agent также не подключается. Всё необходимое агенту настраивайте внутри его профиля.

## Ограничение CPU и памяти

ABX лимитов CPU и памяти не ставит, кроме приватных tmpfs-монтов (`/tmp`, `/var/tmp`, `/run`) с потолком 4 GiB на каждый. Если нужны общие лимиты, запускайте ABX внутри systemd scope:

```sh
systemd-run --user --scope -p MemoryMax=8G -p CPUQuota=400% -- abx run opencode
```

## Решение проблем

| Проблема | Что проверить |
|---|---|
| `must not run as root` | Запускайте без `sudo` |
| Bubblewrap отсутствует или слишком старый | Проверьте `/usr/bin/bwrap --version`; нужен 0.11.1+ |
| Песочница не запускается | Проверьте, что хост разрешает непривилегированные user namespaces |
| Профиль не найден | Проверьте `abx profile show <profile>` и используемый `XDG_DATA_HOME` |
| `private directory "<путь>" must have exact mode 0700` | Выполните `chmod 700` для корня хранилища и `shared` (см. Shared skills) |
| `unsafe Bubblewrap executable` | Бинарник должен быть обычным файлом, исполняемым, без setuid/setgid/sticky-битов, недоступным для записи group/other, принадлежать root |
| `Command: unavailable` / агент не найден | Для `run` и `inspect` установите executable с именем профиля. Для `shell` и `work` такой статус сам по себе не мешает работе |
| Агент через mise не найден | Проверьте `.local/share/mise/shims/<name>` в профиле и доступность самого бинарника `mise` внутри песочницы |
| Shell недоступен | Проверьте login shell в `/etc/passwd`, его системную установку и права на выполнение |
| Проект отклонён | Используйте отдельный каталог проекта вне защищённых путей |
| Программа с хоста не видна внутри `abx shell` | Возможно, она установлена только в home хоста; установите её в профиль или системно |
| `verify` показывает `FAIL` или `UNAVAILABLE` | Прочитайте ошибку конкретной проверки; полная проверка песочницы не завершилась успешно |
| `must not run as root` / `must not run with effective privileges` / `must not run with effective group privileges` | Запускайте обычным пользователем. ABX отвергает эффективный UID или GID, отличающийся от реального; это покрывает `sudo` и setuid/setgid-бинарники. `sg` и `newgrp` меняют реальный и эффективный GID вместе, и эта проверка их не отвергает. |
| `login shell ... is outside read-only system mounts` или `... resolves outside ...` | Оболочка из passwd и её разрешённая цель должны обе лежать в `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64` или `/etc/alternatives`; оболочки в `/snap`, Nix и `~/.local` внутри песочницы не видны |
| `data base ancestor ... is not owned by the invoking user` | Ближайший существующий предок базы ABX — по умолчанию или выбранной через `XDG_DATA_HOME` — должен принадлежать вам; выберите другую базу |

## Коды завершения и сигналы

Для собственных операций ABX использует код `0` при успехе, `1` при ошибке выполнения или проверки и `2` при ошибке синтаксиса CLI. `run`, `shell` и `work` обычно возвращают код дочернего процесса; завершение по сигналу возвращается как `128 + signal`. Команда `verify` сообщает собственный статус (`1` при неуспехе, включая таймауты и прерывания по сигналу), пока пересылка сигналов активна, а не статус дочернего процесса. Вне этого окна — при подготовке до запуска песочницы и снова при зачистке после её возврата — обработчика ABX нет: `SIGQUIT` печатает дамп горутин и завершает лаунчер с кодом `2`, а `SIGINT`, `SIGTERM` и `SIGHUP` — с `128 + signal`, и временные файлы могут остаться. Код выхода `2` дочернего процесса из `run`, `shell` или `work` неотличим от ошибки синтаксиса CLI: статус дочернего процесса возвращается как есть, поэтому агент, завершившийся с `2`, читается как опечатка в команде. Если зачистка падает после того, как дочерний процесс уже завершился ненулевым статусом, этот статус сохраняется, а сообщаемая ошибка соединяет статус потомка с неуспехом зачистки.

Сигналы `SIGINT`, `SIGTERM`, `SIGHUP` и `SIGQUIT`, отправленные самому ABX, передаются процессу-монитору Bubblewrap. `SIGQUIT` — это сигнал, который терминал посылает по `Ctrl+\`, и благодаря пересылке эта клавиша прерывает сессию так же, как `Ctrl+C`. Без пересылки она завершала лаунчер действием по умолчанию и давала код выхода `2`, который это руководство документирует как код ошибки разбора командной строки, так что прерванный запуск читался как опечатка в команде. Bubblewrap не устанавливает обработчик сигналов: он блокирует `SIGCHLD` и читает его через `signalfd`, поэтому пересланный `SIGINT` завершает монитор действием по умолчанию. ABX не передаёт ни `--new-session`, ни отдельную процессную группу, поэтому во время `run` терминальный `Ctrl+C` достигает всей цепочки сразу: payload получает `SIGINT` и может начать завершаться, но смерть монитора вызывает срабатывание parent-death signal, вооружённого внутри песочницы, и оставшиеся процессы песочницы затем завершаются `SIGKILL` — раньше, чем обработчик завершения успевает отработать. Интерактивная сессия `shell` или `work` ведёт себя иначе: login shell включает job control и забирает терминал в собственную процессную группу, поэтому терминальные сигналы остаются внутри песочницы и не доходят ни до ABX, ни до монитора, а сессия завершается через `exit` или `Ctrl+D`, а не кодом `130`; сигнал самому процессу `abx` по-прежнему идёт по пути пересылки. Payload, убитый `SIGKILL`, не может восстановить терминал: если полноэкранная программа или pager оставили его в raw mode или alternate screen, после этого выполните `reset` или `stty sane`. Если песочница умерла, пока её login shell владел терминалом, терминал может остаться с именем передней группы процессов, которой больше нет; `reset` и `stty sane` это не исправляют, а внешний shell может сообщить `EIO` или потерять job control. Откройте новый терминал или переподключитесь, чтобы получить свежую сессию. Несохранённая работа теряется при любом прерывании: всё, что должно пережить прерывание, нужно записывать по ходу дела. При выходе ABX `--die-with-parent` завершает песочницу и оставшиеся в ней процессы, включая фоновые задачи (см. [Безопасность](security.md)).

Сигнал, который уже игнорировался при старте ABX, остаётся игнорируемым: ABX его не ловит и не пересылает, а дочерний процесс наследует этот режим. Именно поэтому `nohup abx run ... &` и `trap '' HUP` в shell переживают закрытие терминала; обычный запуск по-прежнему пересылает `SIGHUP`, и закрытие терминала завершает сессию. `nohup` решает вопрос сигнала, а не терминала: интерактивной сессии, которая должна пережить терминал, место в `tmux` или `screen`.
