# Security model

**English** | [Русский](ru/security.md)

This document describes the boundaries enforced by the current implementation. For normal commands and examples, see [Usage](usage.md).

## What ABX isolates

`run`, `shell`, and `work` use the same sandbox policy. `shell` simply omits the project mount and starts the account's login shell. `work` mounts the same project as `run` but starts the login shell at `/workspace`.

| Resource | `run` / `work` / `verify` | `shell` |
|---|---|---|
| Profile home | `/home/agent`, writable | Same |
| Current project | `/workspace`, writable, cwd | Not mounted |
| Shared skills, if configured | `/home/agent/.agents/skills`, read-only | Same |
| Selected system files | Read-only | Same |
| `/tmp`, `/var/tmp`, `/run` | Private tmpfs, 4 GiB each | Same |
| `/proc`, `/dev` | Private/separate views | Same |
| Network | Shared with host | Shared with host |

Bubblewrap creates separate user, mount, PID, IPC, and UTS namespaces and sets the hostname to `abx`. ABX also passes `--disable-userns`, so code inside the sandbox cannot create another user namespace through Bubblewrap's supported mechanism. ABX passes `--die-with-parent`, so the sandbox processes are killed with SIGKILL when the launcher exits. This covers a running sandbox; a signal arriving while Bubblewrap is still setting up the sandbox, before its parent-death signal is armed, may leave an orphaned sandbox behind. One limit is worth stating plainly. Bubblewrap installs no signal handler: it blocks `SIGCHLD` and reads it through `signalfd`, so any signal ABX forwards terminates the monitor by the default action, which fires the parent-death signal and kills the payload with SIGKILL even while a shutdown handler is running. ABX passes neither `--new-session` nor a separate process group, so a terminal `Ctrl+C` during `run` reaches the monitor and the payload together and behaves the same way. In an interactive `shell` or `work` session the login shell enables job control and takes the terminal for its own process group, so terminal signals stay inside the sandbox and neither the monitor nor ABX receives them; such a session ends with `exit` or `Ctrl+D`, or when `abx` itself is signalled. A background job started inside the sandbox does not outlive the session: the sandbox is its own PID namespace, and when that namespace's init process (pid 1) dies, the kernel kills every process left in it, `nohup` and `setsid` jobs included. Their tmpfs allocations and network access end with the session.

The environment starts empty. ABX sets HOME, USER/LOGNAME, SHELL, PWD, TMPDIR, XDG paths, PATH, and npm/Bun locations. Only terminal/locale/color settings are forwarded from the host: `TERM`, `COLORTERM`, `LANG`, `LANGUAGE`, `TZ`, `NO_COLOR`, `FORCE_COLOR`, and any variable whose name has the form `LC_*` -- `LC_` plus one or more characters from `A-Z`, `0-9`, or `_`. The check is on the name alone: names beyond locale settings pass too. A value carrying a NUL byte is not forwarded, and content is otherwise not validated; the per-value length bound sits under Accepted trade-offs. Each forwarded value is passed to Bubblewrap as a separate `--setenv NAME VALUE` argument, so its value is visible in the monitor's `/proc/<pid>/cmdline` to other local users while it runs. For `shell` and `work`, the login shell reads the profile's startup files. Those files can change the working directory, so the actual directory after startup may differ from the initial one, and `PWD` is not guaranteed to follow it.

Arbitrary host environment variables, including proxy, credential, and loader/runtime injection variables, are not inherited automatically. The host SSH-agent socket is not exposed.

## Files visible from the host

ABX exposes `/usr` read-only and, when present, the compatibility paths `/bin`, `/sbin`, `/lib`, and `/lib64`. It also exposes a limited set of `/etc` resources, when present on the host, needed by typical command-line programs, such as account/group data, DNS configuration, certificates, timezone data, dynamic-loader configuration, OS metadata, shells, and alternatives. Candidates that are missing, pass through a symlink cycle, or contain a non-directory component are skipped silently; `abx inspect` prints the actually discovered list.

The certificate trees are mounted as whole directories. `/etc/ssl` and `/etc/pki` include any `private` subdirectories they contain, with their host modes unchanged; `/etc/ca-certificates` is mounted whole as well. Bubblewrap writes `setgroups=deny` for the user namespace but does not clear the inherited supplementary group list, so a user in a group such as `ssl-cert` can read group-readable keys under those trees. This is same-UID exposure to trusted host configuration, not a privilege gain.

The entire host `/etc`, host home, and host `/run` are not mounted into the sandbox. Base directories that no later mount covers stay writable inside the sandbox as ephemeral scratch; the agent can only plant files there against itself.

ABX does not mount the account home as a whole. The selected profile is mounted writable; `run` and `work` additionally mount only the selected current project writable.

## Filesystem checks

ABX treats its storage and profiles as private data. Required ABX-owned directories must be real directories, belong to the invoking user, and have exact mode `0700` where the policy requires it. Unsafe existing objects are rejected rather than automatically repaired.

The current project is canonicalized before use. ABX rejects projects that overlap the filesystem root, the account home itself, ABX storage, protected system trees, or sensitive home trees (`.config`, `.ssh`, `.gnupg`, `dotfiles`, `.aws`, `.docker`, `.kube`, `.pki`, `.cache`, `.netrc`, `.git-credentials`, `.password-store`, `.npmrc`, `.gem/credentials`, `.local/share/keyrings`, `.mozilla`, and `.thunderbird`).

Selected host sources are opened and retained by file descriptor. Before execution ABX revalidates them, and Bubblewrap receives bind sources through retained FDs rather than reopening the same path. This narrows pathname-replacement races between validation and mounting; it does not make the contents of writable files or directories immutable. Before execution ABX also sweeps every inherited file descriptor above the standard streams and marks it close-on-exec. The descriptors it hands to the child -- the retained mount sources, the retained Bubblewrap binary, and, for `verify`, the descriptor for `/proc/self/exe` -- are already `O_CLOEXEC` when the sweep reaches them and are skipped. The sweep is deliberate: os/exec reinjects an exported descriptor into the child with the flag cleared, so the child still receives each one exactly once, while inheriting it would show the child a second copy under its original number. The same sweep covers ABX's own retained storage descriptors, including the ones not handed to the child, so unrelated host descriptors never reach the sandbox. The original flags are restored on the launcher side afterwards.

The in-memory sandbox `Plan` is structurally validated when it is built and again before Bubblewrap translation. The validator checks the expected system sources, private mounts, profile/project roles, optional skills mount, working directory, command, verification probe layout, environment names and values, and that `PWD` is set exactly once and matches the working directory.

ABX additionally validates the host objects it depends on: the two it executes, the account database it reads, the account home that is the default storage base and the location of the `verify` sentinel, its own storage, and the place the agent executable really lives.

| Object | Check |
|---|---|
| `/usr/bin/bwrap` | Regular file, executable, no setuid/setgid/sticky bits, not writable by group/other, owned by root; before execution the retained canonical target must still be the same inode and pass the same mode check again. The `/usr/bin/bwrap` name is not re-resolved, so retargeting that symlink does not change the checked target. File capabilities (`security.capability`) are not checked; a root-owned `bwrap` carrying them is trusted as part of the fixed binary |
| Login shell from `/etc/passwd` | Resolved target is a regular file, executable by the invoking user, not writable by group/other, no setuid/setgid/sticky bits; both the passwd path and its resolved target must be visible in the sandbox |
| Account home from `/etc/passwd` | A real directory, not world-writable, owned by the invoking UID |
| ABX storage root, profiles directory, profile home, and the optional `shared` directory when skills are configured | Real directories, exact mode `0700` with no setuid/setgid/sticky bits, owned by the invoking UID |
| Profile executable | A regular file, executable by the invoking user, not writable by group/other, no setuid/setgid/sticky bits; its link chain, resolved on the host, must end inside the profile or under a mounted system source, so a link into unmounted host paths is refused before start instead of failing at exec with the tool blamed. The check reads host paths and does not translate symlink targets into sandbox paths: a link whose target is the profile's absolute host path can pass it and still fail at exec time inside the sandbox (see [Usage](usage.md#executable-symlinks)) |
| Mounted system sources (`/usr`, `/etc` files other than `passwd`) | Trusted host configuration: each source is resolved against symlinks, rejected on overlap with the home or storage, and held by descriptor; the source and the intermediate directories leading to it are not checked for owner or group/other-writability (see Accepted trade-offs). The `/etc/ssl` and `/etc/pki` trees are mounted whole, `private` subdirectories included |
| `/etc/passwd` | Regular file, not writable by group or other, no setuid/setgid/sticky bits; its owner is not required to be root. The mode is checked when the account is resolved for every command that needs one, and again when the shell is resolved; revalidation compares identity only |
| Compatibility symlinks (`/bin`, `/sbin`, `/lib`, `/lib64`) | Link text must be a relative path, and the resolved target must land under an already-discovered mounted system source (normally `/usr`; a real non-usrmerge compatibility directory also qualifies) and not overlap the home or storage; the link is not held by descriptor, its mode and owner are not checked, and its text is reverified before execution. A compatibility path that exists as a real directory (a distribution without usrmerge) is a mounted system source: it is held by descriptor and revalidated by identity, with no owner or mode check, like the other system sources |

The account database is reached by two different routes, and which files they read depends on how ABX was built. The login shell is always read from the literal `/etc/passwd`. The account record itself (`home`, `username`) comes from `os/user.LookupId`. The shipped static binary sets `CGO_ENABLED=0`, where `os/user` uses its own implementation and reads that same literal `/etc/passwd`, so the row above covers both routes. Built with cgo, `LookupId` goes through NSS and reads `nsswitch.conf` instead; there a host that resolves `passwd` through `sss` or `ldap` makes the shell lookup fail while `id` and `getent` still report the account correctly, and ABX refuses. Build from source with `CGO_ENABLED=0` to keep both routes covered. A local `/etc/passwd` entry for the invoking UID is required either way; that requirement is stated in [Installation](installation.md) as well.

Ownership of the login shell is deliberately not required: user-managed shells also live under system paths (for example `/usr/local/bin`), and the visibility rule already limits them to mounted system trees. The same applies to the agent executable: its mode and bits are checked, but not its owner, because a package-managed link may end at a file under `/usr` owned by another account, and mounted system sources are trusted host configuration. That visible list is static: a shell whose location is missing on the host is refused during resolution (`login shell "<path>" does not exist`), and one that resolves outside the list is refused as outside the read-only system mounts; neither reaches exec.

The mounted `/etc/shells` is provided for programs inside the sandbox; login-shell validation does not consult it. The built-in checks above are stricter on most systems, and `/etc/shells` on some distributions lists non-system paths.

When the shipped static build resolves the login shell, it touches the account database at least four times: `ResolveAccount` stats it for the mode check, `os/user.LookupId` reads the account record, and `shellFromPasswd` stats it again and reads the shell row. Profile commands resolve only the account record, so they make the first two accesses. Each access resolves the path again, so unlike the Bubblewrap binary -- which ABX opens once and holds the descriptor until execution -- nothing pins the checked file and the read file to the same inode. Replacing the file between any two accesses needs write access to the file or to the directory holding it; the mode check forbids group and other only from writing the file itself, and the containing directory is not checked. A host with a group-writable `/etc` therefore leaves that window open for the group, within the group-writable-ancestor boundary stated under Accepted trade-offs. A host whose account database an unprivileged user owns or can rewrite is therefore outside what ABX protects: that user already controls the host account that ABX reads, and the same file is read again through `os/user` without these checks at all. Holding one descriptor across all accesses would close the window and change nothing else.

## Shared skills

If `<ABX storage>/shared/agents/skills` exists and passes validation, it is mounted read-only at `/home/agent/.agents/skills`.

The shared path is optional. ABX checks the relevant directories and rejects unsafe symlink redirection at the profile mount target. Preparation may leave empty `.agents` / `.agents/skills` directories in the writable profile; the shared content itself remains mounted read-only.

## Verification

`abx verify <profile>` launches the same sandbox backend used for normal execution, with one additional fixed read-only probe executable. It checks observed namespaces, cwd, hostname, environment, private mounts/views, read-only resources, writable profile/project access, and selected access boundaries. The private-object checks include `/proc` and `/dev/shm`; `/run/user` must also not be a separate mountpoint.

The `__probe` entry point is private: it refuses to run unless `/proc/self/exe` and `/abx-probe` identify the same object and `/abx-probe` is mounted read-only. Inside the sandbox `/abx-probe` is the read-only mount of the ABX binary; this checks the mode the probe runs under, not the origin of the call.

For read-only resources, the probe checks the mount flags at each selected mountpoint in `/proc/self/mountinfo`. It does not independently inspect every nested mount or attempt writes to those resources. Read-only enforcement is delegated to Bubblewrap; a `PASS` for a parent mountpoint is not a separate verification of all its nested mounts.

A successful `verify` is evidence about that invocation and host state. It is not a permanent guarantee about later runs.

## Remaining risks

- The agent can modify or delete anything in the writable profile and selected project.
- Networking is shared, so sandboxed code can access network services reachable from the host and can transmit data it can read.
- Project contents are not recursively sanitized. Projects may contain sockets, hard links, nested mounts, or intentionally dangerous source/build files.
- The sandbox uses the caller's terminal directly. Terminal escape sequences and host-specific terminal ioctls remain part of the risk surface; ABX does not provide terminal-session isolation.
- ABX does not define a seccomp policy or cgroup resource quotas. ABX sets the 4 GiB cap only on its own three tmpfs mounts, `/tmp`, `/var/tmp` and `/run`. Everything else the sandbox gets as writable without a cap: the `--dev` mount builds its own tmpfs, and the sandbox root is created by Bubblewrap, for which ABX sets no size at all. Security still depends on the Linux kernel, Bubblewrap, the host configuration, and the software executed inside the sandbox.
- A hostile process running concurrently as the same host UID may still race changes in data that the user can modify. Retained descriptors and revalidation reduce important pathname-replacement windows but are not a complete same-UID adversary model. The known residual windows — agent-executable or login-shell replacement between inspection and execution, profile entries changing between listing and inspection, data-base components appearing between canonicalization and use, and pathname-based metadata rechecks — are accepted as documented and are not tracked as findings. Mounts use the retained descriptors, so a late swap cannot redirect the final object that was retained; replacing an intermediate project symlink before it is opened remains the window described under Path assumptions.
- Some failed operations may leave directories or verification probe files behind. ABX avoids recursive automatic rollback that could delete unrelated user data.

## Accepted trade-offs

The following are deliberate current boundaries rather than pending implementation work:

- **Runtime isolation:** networking is shared, the caller terminal is used directly without terminal-session isolation, no seccomp policy or resource quotas are defined (ABX sets the 4 GiB cap only on its own three tmpfs mounts, `/tmp`, `/var/tmp` and `/run`; the `--dev` mount builds its own tmpfs, and the sandbox root created by Bubblewrap gets no size at all), and project contents and nested mounts are not recursively sanitized. The cgroup namespace is shared with the host, so `/proc/self/cgroup` shows the host's slice or scope; `abx inspect` prints `cgroup namespace: shared with host`. The environment is sanitized only against NUL bytes, so a host value carrying a newline reaches the agent unchanged; forwarded values -- `TZ`, `LANG`, `LANGUAGE`, `LC_*`, `TERM`, `COLORTERM`, `NO_COLOR` and `FORCE_COLOR` -- stay unrestricted in content but are bounded to 64 KiB per value; `verify` also caps its whole probe payload at 64 KiB, so a value near the per-value bound can leave no room for the fixed probe data even though `run`, `shell`, and `work` accept it; libc reads the locale ones as files under `/usr/share`; forwarded values travel as `--setenv` arguments in the monitor's argv, as described under What ABX isolates. The identity of the process inside the sandbox is neither documented nor checked.
- **Path assumptions:** projects overlapping protected system trees are rejected including subdirectories (`/bin`, `/boot`, `/dev`, `/etc`, `/lib`, `/lib64`, `/opt`, `/proc`, `/root`, `/run`, `/sbin`, `/sys`, `/usr`, `/var`, `/srv`, `/mnt`, `/media`, `/snap`); `/tmp`, `/var/tmp`, and `/dev/shm` are rejected as exact paths, while `/var/tmp` and `/dev/shm` are also rejected as subdirectories of `/var` and `/dev`; sibling homes outside the real home are rejected only under `/home`; a project inside the invoking user's own home is still rejected when that home itself sits under a protected tree such as `/var` — there is no carve-out, so `run` and `work` cannot be used from such a home; intermediate project-symlink replacement and the early-start signal race are not fully closed; system symlink aliases rely on trusted host configuration; compatibility links must be relative and resolve under an already-discovered mounted system source; a usrmerge layout pointing inside `/usr` is the usual case, while a non-usrmerge link to a real compatibility directory is accepted when that directory is itself a system source and refused otherwise; and the sensitive-home denylist is intentionally finite. The account home is checked for ownership and world-writability; it is not checked for setuid or setgid bits as a home. The ancestor rule below also applies to the home directory whenever no directory of the data base path exists yet and the walk therefore stops at it. When skills are configured, the two preparation directories below `shared` (`agents` and `agents/skills`) are checked only as real directories, not for exact mode; `shared` itself is exact `0700`. Missing storage components are created with mode `0700`; the nearest existing ancestor of the data base -- the default `~/.local/share` in the passwd home or a custom absolute `XDG_DATA_HOME` -- must already be a user-owned directory that is not world-writable unless it carries the sticky bit, and must carry no setuid or setgid bit: a setgid directory makes everything created under the storage root inherit a group the check never inspects. The account home must be owned by the invoking UID. `/etc/passwd` is not required to be owned by root: it must be a regular file without setuid/setgid/sticky bits that group and other cannot write, because the entry it yields names the account home used as the default storage base and the location of the `verify` sentinel. Replacing it between any two accesses needs write access to the file or to its directory; the file-mode check covers only the file itself, and a group-writable `/etc` is accepted like any group-writable ancestor — see the account-database paragraph above. Group-writable ancestors are accepted: that is a team policy, not an attack, and refusing it breaks machines running umask 002. That acceptance extends to the intermediate directories of the login shell and the agent executable: ABX checks the final file, not the directories leading to it, so a group member able to write a parent directory could substitute the binary a session runs. Mounted system sources other than `/etc/passwd` are trusted configuration in full: neither the final file nor the directories leading to it are checked for owner or group/other writability, as the filesystem table above states. The mounted `/etc/ssl` and `/etc/pki` trees include their `private` subdirectories, and supplementary groups are preserved, so group-readable keys remain readable to members of those groups. `/etc/passwd` is the exception: its mode is checked when the account and the shell are resolved, because its owner need not be root. Closing the gap would break the same team machines, so the risk is accepted as documented. The profile executable may be a symlink into a mounted system path such as `/usr`, or into the profile itself, which is how a package manager installs it; a link resolving outside both is refused while the profile is resolved, because nothing is mounted there and the session would otherwise fail at exec time. The current project is not constrained by ownership or mode at all — team checkouts, shared volumes, and filesystems without POSIX modes (which report `0777` for everything) are legitimate.
- **Verification and diagnostics:** `verify` is a smoke test rather than a complete security attestation; probe metadata travels through argv; cleanup races and residue remain best-effort; Bubblewrap setup errors and payload exit code `1` are not distinguished; and the retained Bubblewrap FD is accepted. The private `__probe` entry point is guarded by the mode it runs under (the binary executing as the read-only `/abx-probe` mount), not by the origin of the call.
- **Release and CI:** source packaging assumes a clean checkout, CI action and tool versions, including the Bubblewrap package in the live gate and the linter configuration schema, float, live tests gate release tags rather than pull requests, and archives are not byte-for-byte reproducible or signed/attested.

Back up important project and profile data according to your normal workflow; writable access is intentional.
