# Инструкции для разработчиков и агентов

[English](AGENTS.md) | **Русский**

Инструкции действуют во всём репозитории. Основная версия — английская; этот файл является переводом. Явные инструкции пользователя имеют приоритет.

## Перед изменением кода

Прочитайте README и относящиеся к задаче руководства в docs. Для изменений исполнения, путей, mounts или окружения прочитайте docs/security.md и docs/architecture.md, а также затронутые реализацию и тесты. Сохраняйте посторонние изменения и ограничивайте каждую правку конкретной проблемой.

У каждого руководства свой вопрос: [Использование](docs/ru/usage.md) — пользовательское поведение, [Модель защиты](docs/ru/security.md) — границы защиты, [Архитектура](docs/ru/architecture.md) — структура и обязанности пакетов. Проверяйте соответствие реализации и тестов, а не полагайтесь на этот файл. Исторические проектные материалы служат справкой, а не дополнительными требованиями. Совместимость с прежними форматами профилей и CLI не гарантируется.

## Реализация

- Предпочитайте прямой Go-код, конкретные типы, небольшие функции и явное владение ресурсами. Абстракции добавляйте по доказанной необходимости; избегайте запасных backend-ов, реестров, слоёв конфигурации и всеобъемлющей защитной обвязки без реальной задачи.
- Сохраняйте обязанности пакетов: cli разбирает аргументы, host выбирает и проверяет источники, sandbox строит политику, bwrap исполняет, app координирует, probe наблюдает.
- `run`, `shell` и `work` используют одну общую базовую политику изоляции и различаются только тем, что подключают и что запускают; `verify` переиспользует эту политику, а не строит отдельную песочницу. Их текущее поведение описано в [Архитектуре](docs/ru/architecture.md) — читайте там, а не полагайтесь на этот файл.
- Сохраняйте вызов `Plan.Validate()` после построения плана и перед переводом в аргументы Bubblewrap. Сохраняйте структурные проверки ожидаемых источников, mounts, рабочего каталога и структуры команды/probe.
- Передавайте аргументы процессов структурированным argv. Не подставляйте значения пользователя, проекта, профиля или агента в shell-команду.
- Сохраняйте удерживаемые дескрипторы источников и владение ими до завершения исполнения. Не заменяйте FD mounts повторным открытием путей. Подготовка выполняется после проверки runtime; точно сообщайте ошибки подготовки, исполнения и очистки.
- Не ослабляйте проверки молча, не исправляйте существующие права и не удаляйте пользовательские данные рекурсивно ради rollback.
- Учитывайте документированные остаточные риски: не обещайте полной защиты от гонок с процессами того же uid и не создавайте обвязку, подразумевающую такую гарантию.
- Ориентируйтесь на актуальный ubuntu-latest и live-проверки на CachyOS. Не добавляйте поддержку старых ядер, разбор строки версии ядра или новые runtime-зависимости без конкретного требования задачи.

## Проверки

Для существенных изменений добавляйте направленные проверки поведения и регрессий, особенно границ путей, прав, времени жизни ресурсов и обработки ошибок. Не пишите тесты лишь для повторения реализации или достижения процента покрытия.

Во время работы запускайте относящиеся к изменению тесты; для любых изменений на Go, включая тесты, — `make check`: форматирование и линтер проверяют и тестовые файлы, а коммит только с тестами уже ронял у нас `make check`. При изменении изоляции, запуска процессов, обработки сигналов, рабочего каталога или времени жизни сессии нужен `make live` на поддерживаемом хосте под обычным пользователем, даже если настройки namespaces и mounts не меняются. Если такого окружения нет, сообщите о недостающей проверке и дайте конкретный следующий шаг; не выдавайте имитации и пропуски за успешный live-прогон. Для изменений только документации проверяйте ссылки и содержание; для упаковки — созданные архивы.

Тесты используют временное хранилище. Не создавайте тестовые профили в настоящем home пользователя и не подключайте рабочий профиль с записью ради теста.

## Коммиты

Один коммит — одно дело. Заголовок пишется как `<тип>(<область>): <описание>` — строчными, без точки в конце, не длиннее 72 символов вместе с префиксом. Всё более длинное выносится в тело. Это [Conventional Commits](https://www.conventionalcommits.org/) с одним дополнением.

| Тип | Для чего |
|---|---|
| `feat` | новая возможность, видимая пользователю |
| `fix` | дефект |
| `docs` | только документация, комментарии в коде включительно |
| `test` | только тесты |
| `refactor` | перестройка без изменения поведения |
| `perf` | производительность |
| `build` | сборка, упаковка, зависимости, линтеры |
| `ci` | пайплайны и автоматизация |
| `chore` | прочее, невидимое пользователю |
| `revert` | откат изменения |
| `release` | выпуск версии; расширение спецификации |

Используемые области: `host`, `sandbox`, `bwrap`, `app`, `cli`, `probe`, `profile`, `packaging`, `docs`, `ci`, `live`. Область необязательна.

Ломающее изменение помечайте `!` после типа и/или подвалом `BREAKING CHANGE:` с указанием, что изменилось и почему. Сообщения — на английском.

Каждое пользовательское изменение получает запись в `CHANGELOG.md` в раздел `Unreleased` **тем же коммитом, что и изменение**. Коммит только с тестами, ничего не меняющий для пользователя, — нет. Коммит выпуска переносит накопленные записи в раздел версии. Если пользовательское изменение уже ушло в историю без записи, не переписывайте тот коммит: допишите запись в `Unreleased` отдельным коммитом, в сообщении которого сказано, что это позднее дополнение, и пометьте саму запись, если изменение уже вышло в релизе.

## Документация и поставка

- README.md и docs/*.md ведутся на английском, README.ru.md и docs/ru/*.md — синхронный русский перевод. AGENTS.ru.md должен соответствовать английской версии. Переходы между языками должны работать и в упакованных артефактах. AGENTS.md и AGENTS.ru.md включаются только в исходные архивы; пользовательские примеры установки и использования используют имя программы abx.
- Сверяйте каждое фактическое утверждение документа с реализацией — в том же коммите, где меняется код. При отдельном проходе по документации находится заметно меньше: в разборе перед 0.8.24 каждый настоящий дефект сидел в документе, который только что правили, а самый большой документ, которого не касались, не содержал ни одного.
- CHANGELOG.md ведётся только на английском, опубликованная история сохраняется. При выпуске переносите записи в раздел версии и обновляйте `internal/app/VERSION` — единственный источник версии выпуска.
- [Руководство по выпускам](docs/ru/releases.md) — это процедура выпуска, включая объяснение, почему тег версии нельзя отправлять с `--force`.
- Команды в документации должны использовать синтаксис POSIX sh и fenced-блоки sh. Не включайте разовые логи, тестовые проекты и собранные бинарники в исходный архив.
- CI остаётся простым: проверки при push веток и pull requests, артефакты только при push тегов версий. Используйте плавающие теги версий actions без SHA (для пинов в `uses:`; пины исходников вроде коммита Bubblewrap — отдельно). Не добавляйте публикацию GitHub Release и права записи в репозиторий попутно.
- Сохраняйте исполняемый режим 0755 для scripts/*.sh и включайте оба языка документации в упаковку.
- Сообщайте об изменениях, реально выполненных проверках и оставшихся ограничениях. При выдаче архива для скачивания указывайте его SHA-256.

## Когда спрашивать пользователя

Продолжайте обычную реализацию и обратимые проверки в пределах разрешённой задачи. Решение пользователя требуется лишь при неразрешённом выборе, существенно меняющем запрошенное поведение, границы защиты, обращение с данными или объём публикации. Ранее принятые решения сохраняют силу.
